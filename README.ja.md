# kikori

[English](README.md) | 日本語

kikori (木こり) は、WCAG 2.2 の達成基準を、実際のブラウザを動かして検証する MCP サーバーです。
Claude Code などのエージェントから呼び出すと、指摘が達成基準の番号と CSS セレクタつきで返るため、そのまま修正に進めます。

機械的に判定できない達成基準は、判断材料とスクリーンショットを返し、呼び出したモデルに判断させます。自動検査とモデルの判断を合わせて、すべての達成基準に結論を出せます。

名前は、斧 (axe) を振るう木こりから取りました。axe-core を道具として使い、axe だけでは届かない検査まで行います。Deque Systems 社および axe-core の公式の製品ではありません。

## 検査できること

| ツール | 達成基準 | 調べる内容 |
|---|---|---|
| `audit_site` | WCAG 2.2 または 2.1 の全達成基準 | 複数のページを監査し、ページどうしの一貫性も比べます |
| `audit_page` | WCAG 2.2 または 2.1 の全達成基準 | 下の検査をすべて実行し、達成基準ごとの状態を一覧で返します |
| `check_axe` | axe-core が対応する達成基準 | 代替テキスト、コントラスト、ラベル、ARIA、言語指定などの不備を検出します |
| `check_reflow` | 1.4.10 リフロー | 幅 320px で表示し、横スクロール、画面の外にはみ出す要素、切れる文字を検出します |
| `check_text_spacing` | 1.4.12 テキストの間隔 | 行の高さや字間を広げ、その前後を比べて、切れた文字と重なった文字を検出します |
| `check_keyboard_focus` | 2.1.1 / 2.1.2 / 2.4.3 / 2.4.7 / 2.4.11 / 2.4.12 / 2.4.13 / 3.2.1 | Tab キーでページを一巡し、フォーカスの順序、表示の有無、隠れ、抜け出せない箇所、フォーカスだけで起きる画面の移動を調べます |
| `check_presentation` | 2.5.5 / 2.5.8 / 1.4.8 / 2.2.2 / 1.4.2 / 1.3.5 | 小さいターゲットや間隔の足りないターゲット、文章の体裁、動き続けるアニメーション、音声つきの自動再生、autocomplete のない入力欄を検出します |
| `check_interaction` | 1.4.13 / 2.1.4 / 3.2.2 / 2.5.1 / 2.5.2 / 2.5.4 / 2.5.7 / 3.3.8 / 1.4.11 / 2.3.1 / 4.1.3 | ホバー、文字キー、入力欄の変更を実際に試し、イベントリスナー、境界のコントラスト、ドラッグ操作、認証を妨げる指定も調べます |
| `collect_evidence` | 内容を見た判断が要る達成基準 | 答えるべき問い、不適合とする条件、判断材料、ページ全体のスクリーンショットを返します |
| `capture_screenshot` | - | ページや要素のスクリーンショットを返します。細部を確かめるときに使います |

監査の対象は、既定では WCAG 2.2 です。WCAG 2.1 を対象にするには、`wcag: "2.1"` を渡します。そのとき、2.2 で追加された達成基準のうち検査したものは `beyondTarget` に分けて返し、判定には含めません。

| WCAG 2.2 で追加された達成基準 | レベル | kikori の扱い |
|---|---|---|
| 2.4.11 隠されないフォーカス (最低限) | AA | フォーカス中の要素の全体が別の要素に隠れると、不適合にします |
| 2.4.12 隠されないフォーカス (高度) | AAA | 一部でも隠れると、不適合にします |
| 2.4.13 フォーカスの外観 | AAA | outline が 2px より細いか、指定がないとき、確認を求めます |
| 2.5.7 ドラッグ動作 | AA | ドラッグで操作する要素について、確認を求めます |
| 2.5.8 ターゲットのサイズ (最低限) | AA | 24 × 24px に届かず、隣との間隔も足りないターゲットを、不適合にします |
| 3.2.6 一貫したヘルプ | A | `audit_site` が、問い合わせやヘルプへの案内の位置がページによって違うと、不適合にします |
| 3.3.7 冗長な入力 | A | `audit_site` が、同じ入力欄が複数のページにあると、確認を求めます |
| 3.3.8 アクセシブルな認証 (最低限) | AA | 貼り付けを拒否するパスワード欄を不適合にし、`autocomplete="off"` と CAPTCHA について確認を求めます |
| 3.3.9 アクセシブルな認証 (高度) | AAA | CAPTCHA について確認を求めます |

4.1.1 構文解析は WCAG 2.2 で廃止されたので、2.1 を対象にしたときだけ一覧に出ます。

## audit_page の読み方

`audit_page` は、目標のレベル (`A`、`AA`、`AAA`。既定値は `AA`) までの達成基準をすべて並べ、それぞれに状態を付けます。WCAG 2.2 ではレベル AA で 55 件、AAA で 86 件です。WCAG 2.1 では 50 件と 78 件です。

| 状態 | 意味 |
|---|---|
| `fail` | 不適合が見つかりました |
| `review` | 自動では判定しきれない箇所が見つかりました。指摘を見て判断します |
| `needs_judgment` | 内容を見た判断が必要です。`collect_evidence` で材料を集められます |
| `no_issue_found` | 自動検査の範囲では問題が見つかりませんでした。適合の保証ではありません |
| `judged_pass` | 渡された判断で、満たしているとされました |
| `inapplicable` | 対象になる要素がページになく、該当しないと推定しました |
| `manual` | 材料を集める手段がなく、人の確認が必要です |

`conformance.verdict` は次のいずれかになります。

- `nonconformant`: 不適合が見つかりました。
- `undetermined`: 不適合は見つかりませんでしたが、確認が残っています。
- `no_failure_found`: 自動検査と渡された判断を合わせて、すべての達成基準で不適合が見つかりませんでした。

## モデルに判断させる流れ

代替テキストが内容に合っているか、見出しが続く内容を表しているかは、機械的には判定できません。こうした達成基準は、次の手順で呼び出し側のモデルが判断します。

1. `audit_page` を実行します。判断が要る達成基準は `needs_judgment` になります。
2. `collect_evidence` を実行します。達成基準ごとに、問い (`question`)、不適合とする条件 (`failWhen`)、`unsure` と答える場合 (`unsureWhen`)、材料 (`evidence`) が返ります。ページ全体のスクリーンショットも付きます。
3. 細部を見たいときは、`capture_screenshot` で要素を拡大します。
4. 判断を `judgments` に入れて、`audit_page` をもう一度実行します。

```json
{
  "url": "http://localhost:3000/",
  "judgments": [
    { "id": "2.4.4", "verdict": "pass", "reason": "リンクの文言だけで行き先が分かる" },
    { "id": "1.1.1", "verdict": "fail", "reason": "代替テキストがファイル名になっている", "evidence": "#hero, alt=\"IMG_0042.jpg\"" },
    { "id": "2.4.9", "verdict": "unsure", "reason": "「詳細」というリンクが 2 つあり、行き先の URL が違うが、行き先の内容を読めなかった" }
  ]
}
```

`verdict` は `pass`、`fail`、`inapplicable`、`unsure` のいずれかです。自動検査で不適合が見つかった達成基準は、`pass` を渡しても不適合のままです。

モデルの判断が安易に不適合にならないよう、次の決まりを設けています。

- `fail` には、根拠にした箇所を `evidence` に書きます。ページのセレクターか文言です。書かれていない `fail` は `review` になります。
- `unsure` は、材料だけでは決められないことを表します。その達成基準は `review` になり、人の確認に回ります。

`no_failure_found` は、適合の証明ではありません。自動検査は調べられる範囲に限りがあり、判断にはモデルによるものが含まれます。適合を表明する前に、支援技術を使った人による確認を行ってください。

`collect_evidence` が材料を返す達成基準は次のとおりです。

| 達成基準 | 材料 |
|---|---|
| 1.1.1 非テキストコンテンツ | 画像 (`canvas` と `svg` を含む) の一覧。名前と、支援技術から隠されているかどうかが付きます |
| 1.3.2 意味のある順序 | HTML の順に並べた文章と、見た目の順序と食い違う箇所 |
| 1.3.3 感覚的な特徴 | 形、色、位置、音に触れている文章の候補 |
| 1.4.5 / 1.4.9 文字画像 | 画像と背景画像の一覧 |
| 1.4.11 非テキストのコントラスト | アイコンの数。入力欄の境界は `check_interaction` が測ります |
| 2.3.1 3 回の閃光、又は閾値以下 | 動画、GIF、canvas の一覧 |
| 2.4.2 ページタイトル | タイトル、最初の見出し、本文の一部 |
| 2.4.4 / 2.4.9 リンクの目的 | リンクの文言と、文言だけでは分からないものの前後の文脈 |
| 2.4.6 見出し及びラベル | 見出しとラベルの一覧 |
| 2.5.1 / 2.5.2 | ドラッグできる要素の一覧。フレームワークがイベントをまとめて受けるページで使います |
| 3.1.1 / 3.1.2 言語 | `lang` 属性と、それが付いた部分の文章 |
| 3.3.1 エラーの特定 | 誤りとして示された入力欄と、それに付いたメッセージ |
| 4.1.3 ステータスメッセージ | ライブリージョンとフォームの一覧 |

## audit_site で複数のページを監査する

1 ページだけでは判定できない達成基準を、ページどうしを比べて調べます。`judgments` も受け取り、サイト全体の一覧に反映します。

| 達成基準 | 調べる内容 |
|---|---|
| 3.2.3 一貫したナビゲーション | 同じ名前の `nav` 要素の中で、共通する項目の並び順がページによって変わらないか |
| 3.2.4 一貫した識別性 | ヘッダー、フッター、ナビゲーションの中で、同じ行き先のリンクに違う名前が付いていないか |
| 2.4.2 ページタイトル | 違うページに同じタイトルが付いていないか |
| 2.4.5 複数の手段 | ナビゲーション、サイト内検索、サイトマップのうち 2 つ以上があるか |
| 2.4.8 現在位置 (AAA) | パンくずリストか `aria-current="page"` があるか |
| 3.2.6 一貫したヘルプ | 問い合わせやヘルプへの案内が、ほかの繰り返し現れるリンクに対して同じ位置にあるか |
| 3.3.7 冗長な入力 | 同じ入力欄が複数のページにないか |

対象のページは 2 通りの方法で指定できます。

- `url` だけを渡すと、そのページにある同じサイト内のリンクを `maxPages` (既定値は 5、上限は 20) までたどります。
- `urls` に一覧を渡すと、リンクをたどらず、`url` とその一覧だけを検査します。

結果の `criteria` は、全ページを通した状態です。1 ページでも不適合があれば `fail` になります。ページどうしを比べた指摘は `crossPage` に、ページごとの指摘は `pages` に入ります。

ページごとに 7 回ブラウザを起動するため、1 ページあたり 5 秒前後かかります。

## 使い方

Node.js 22 以上が必要です。

Claude Code に登録します。準備はこれだけです。

```sh
claude mcp add kikori -- npx -y kikori
```

最初の検査のときに、kikori が使うブラウザ (ヘッドレスの Chromium、ディスク上で約 300 MB) をダウンロードします。ダウンロードは 1 回だけで、回線によって数秒から 1 分ほどかかります。

- Linux では、ブラウザにシステムのライブラリが必要なことがあります。`npx kikori install --with-deps` を実行すると、ブラウザとあわせて入ります。
- コンテナのイメージを作るときなど、前もってブラウザを入れておくには、`npx kikori install` を実行します。
- 自動でのダウンロードを禁じるには、`--no-auto-install` を付けてサーバーを起動します。

ダウンロードは、kikori が依存している Playwright が行うので、ブラウザの版が食い違いません。`npx playwright install` を直接実行すると、別の版の Playwright 向けのブラウザが入ることがあります。

### エージェント用のスキル (任意)

このリポジトリには、kikori での監査の進め方をエージェントに教えるスキルも入っています。最初に呼ぶツール、状態の読み方、判断材料の集め方と判断の渡し方、言ってはいけないことを説明します。[skills CLI](https://github.com/vercel-labs/skills) で入れられます。

```sh
npx skills add vivil/kikori
```

スキルが追加するのは手引きだけです。MCP サーバーは、上の手順で別に登録します。

登録後は、次のように頼めます。

```text
http://localhost:3000/ を audit_page でレベル AA まで検査して、fail の指摘を直して
```

## 起動時のオプション

検査結果の言語と、検査してよい範囲を、起動時に決められます。

検査結果には画面の画像や文章が含まれます。呼び出し側のモデルがだまされても、社内のサーバーや手元のファイルを読み出す経路にならないよう、開いてよい範囲を起動時に決められます。この設定はツールの引数からは変えられません。

| オプション | 環境変数 | 説明 |
|---|---|---|
| `--lang <ja\|en>` | `KIKORI_LANG` | 検査結果やエラーの文面に使う言語。指定しないときは、環境の言語設定が日本語なら `ja`、それ以外は `en` です |
| `--allow-host <ホスト>` | `KIKORI_ALLOWED_HOSTS` | 開いてよいホスト。複数回の指定と、カンマ区切りができます。指定しないときは、`localhost` と `127.0.0.1` だけを開きます。`*` を指定すると、すべてのホストを開きます |
| `--allow-frame-host <ホスト>` | `KIKORI_ALLOWED_FRAME_HOSTS` | ページの中の iframe が読み込んでよいホスト。指定しないときは、iframe の読み込みをすべて止めます |
| `--file-root <パス>` | `KIKORI_FILE_ROOT` | `file` の URL で開いてよいディレクトリ。既定では、サーバーを起動したディレクトリです |
| `--no-file` | `KIKORI_NO_FILE=1` | `file` の URL を受け付けません |
| `--storage-state <パス>` | `KIKORI_STORAGE_STATE` | ログイン済みの状態を保存したファイル。その Cookie とローカルストレージを持った状態でページを開きます |
| `--no-auto-install` | `KIKORI_NO_AUTO_INSTALL=1` | ブラウザがないとき、自動ではダウンロードしません |

何も指定しなければ、自分のコンピューターで動くサーバー (`localhost`、`*.localhost`、`127.0.0.1`、`[::1]`) だけを検査できます。開発中のサイトを検査するなら、設定は要りません。

公開しているサイトを検査するときは、そのホストを指定します。`--allow-host` を指定すると既定の一覧は使われなくなるので、開発サーバーも検査するなら `localhost` を並べて書いてください。

```sh
claude mcp add kikori -- npx -y kikori --allow-host localhost --allow-host example.com
```

ホストの書き方は 3 通りあります。

- `localhost:3000`: そのポートだけに一致します。
- `example.com`: すべてのポートに一致します。サブドメインには一致しません。
- `*.example.com`: サブドメインに一致します。`example.com` 自体には一致しません。

制限は次の場面で働きます。

- ツールに渡された URL が一覧にないとき、ページを開かずにエラーを返します。
- ページの中のリンクやスクリプトが、一覧にないホストへ移動しようとしたとき、その移動を止めます。
- ページが、一覧にないホストから画像やスクリプトを読み込もうとしたとき、その読み込みを止めます。
- 一覧にあるホストが、ほかのホストへ転送したとき、結果を返さずにエラーにします。

画像、スクリプト、スタイル、通信 (fetch や WebSocket) の読み込み先も、同じ一覧に従います。一覧にないホストからは何も読み込みません。

読み込みを止めたときは、結果の `notes` に宛先が入ります。フォントやスタイルを CDN から読み込むページでは、見た目が実際と違った状態で検査されます。`notes` に出たホストを `--allow-host` に足してください。

```sh
claude mcp add kikori -- npx -y kikori --allow-host localhost --allow-host fonts.googleapis.com --allow-host fonts.gstatic.com
```

すべてのホストを開けるようにするには、`--allow-host '*'` を指定します。

### iframe

iframe の読み込みは、既定ではすべて止めます。検査対象のページが社内のサーバーを iframe に埋め込んでいると、その中身がスクリーンショットに写り込むためです。`srcdoc` や `data:` のように、親のページ自身が中身を持つ iframe は止めません。

読み込みを止めたときは、結果の `notes` に件数と宛先が入ります。iframe の中身は、検査にも画像にも含まれません。

iframe を読み込ませるには、`--allow-frame-host` で宛先を指定します。

- `self`: 検査しているページと同じホストの iframe を許可します。
- `player.example.com` や `*.example.com`: そのホストの iframe を許可します。書き方は `--allow-host` と同じです。
- `*`: すべての iframe を許可します。

```sh
claude mcp add kikori -- npx -y kikori --allow-host localhost:3000 --allow-frame-host self
```

`--allow-frame-host` は `--allow-host` とは別の一覧です。動画の埋め込み先を iframe として許可しても、そのホストを直接検査できるようにはなりません。

`file` の URL で開けるのは、許可したディレクトリの中にある `.html`、`.htm`、`.xhtml` のファイルだけです。

### ログインが必要なページ

ログインが必要なページを検査するには、ログイン済みの状態をファイルに保存し、`--storage-state` で渡します。ファイルは Playwright の storageState 形式で、Cookie とローカルストレージが入ります。

作り方の 1 つは、Playwright のコード生成ツールです。ブラウザが開くので、そこでログインしてからウィンドウを閉じます。

```sh
npx playwright codegen --save-storage=auth.json https://app.example.com/login
```

そのファイルとホストを指定して、kikori を起動します。

```sh
claude mcp add kikori -- npx -y kikori --allow-host app.example.com --storage-state /path/to/auth.json
```

次の点に注意してください。

- ファイルにはセッションの Cookie が入ります。パスワードと同じように扱い、バージョン管理に含めないでください。
- 検査用のアカウントを使ってください。結果には、そのアカウントで見える文章と画面の画像が含まれ、モデルに渡されます。
- 読み込むのは、`--allow-host` で指定したホストに属する Cookie とローカルストレージだけです。ファイルのそれ以外の部分は使いません。
- セッションは、そのアカウントとして操作するのに使えてしまいます。そのため `check_interaction` は、ログイン済みの状態でキー入力、ホバー、入力欄の変更を試す間、通信をすべて止め、開いている WebSocket も閉じます。そのアカウントの権限では、何も実行されません。この間、通信して取得するホバーの内容は検出できません。
- ログイン済みの状態では、`audit_site` はリンクを自動ではたどりません。リンクの中に、ログアウトや削除を行うものがありうるためです。検査するページは `urls` で指定してください。
- ページを GET で開くだけで状態が変わる作りのサイトでは、指定したページを開くことで影響が出ることがあります。
- kikori はファイルを読むだけで、更新しません。セッションが切れると、ページがまたログイン画面へ移動するようになります。そのときは、ファイルを作り直してください。

## 入力

どのツールも `url` が必須です。`http`、`https`、`file` の URL を指定できます。

| 引数 | 対象 | 説明 |
|---|---|---|
| `url` | すべて | 検査するページの URL |
| `waitForSelector` | すべて | 読み込み後、この要素が現れるまで待ちます。SPA の描画待ちに使います |
| `waitMs` | すべて | 読み込み後に追加で待つ時間 (ミリ秒) |
| `urls` / `maxPages` | `audit_site` | 検査するページの一覧と、ページ数の上限 |
| `level` | `audit_site`、`audit_page`、`check_axe` | 目標とする適合レベル (`A`、`AA`、`AAA`)。既定値は `AA` |
| `wcag` | `audit_site`、`audit_page`、`check_axe` | WCAG のバージョン (`2.2` または `2.1`)。既定値は `2.2` |
| `judgments` | `audit_site`、`audit_page` | モデルや人が下した判断の一覧 |
| `criteria` / `screenshot` | `collect_evidence` | 材料を集める達成基準と、スクリーンショットを付けるかどうか |
| `selector` / `fullPage` | `capture_screenshot` | 撮影する要素と、ページ全体を撮るかどうか |
| `width` / `height` | 個別の検査 | ビューポートの大きさ。リフローの既定値は 320 × 256、ほかは 1280 × 720 |
| `maxSteps` | `check_keyboard_focus` | Tab キーを押す回数の上限。既定値は 150 |

## 出力

結果は JSON で返ります。個別の検査は、次の形で指摘を返します。

```json
{
  "check": "reflow",
  "url": "http://localhost:3000/",
  "viewport": { "width": 320, "height": 256 },
  "summary": { "fail": 1, "review": 0 },
  "checked": ["1.4.10"],
  "findings": [
    {
      "sc": { "id": "1.4.10", "name": "リフロー", "level": "AA", "since": "2.1" },
      "severity": "fail",
      "selector": "#wide",
      "message": "幅 320px で右に 580px はみ出し、ページに横スクロールが発生しています。",
      "details": { "overflowPx": 580, "text": "幅を固定した領域です。", "viewportWidth": 320 }
    }
  ]
}
```

`severity` は 2 種類あります。

- `fail`: 機械的に確認できた不適合です。
- `review`: 人の判断が必要な箇所です。表のはみ出しのように、例外にあたる可能性があるものを含みます。

`check_keyboard_focus` は `data.sequence` にフォーカス順の一覧を返します。順序が意味の通るものかは、この一覧を見て判断してください。

## 検査のしくみと限界

- リフローは、幅 1280px の状態を基準にして幅 320px と比べます。もとから切れている文字は報告しません。
- テキスト間隔は、スタイルを上書きする前後を比べます。もとから重なっている文字は報告しません。
- フォーカス表示は、フォーカス中と外した直後の画面を撮影して比べます。途中で一度フォーカスを外すため、`blur` で入力エラーを表示するページでは結果がずれることがあります。
- iframe の読み込みは、既定では止めます。`--allow-frame-host` で許可した場合も、iframe の中の要素は axe とフォーカスの検査の対象外です。
- 行の長さは、和文を 1 文字 1em、欧文を 1 文字 0.5em として見積もった概算です。
- `audit_page` は 1 ページ単位です。複数のページを比べる達成基準 (3.2.3、3.2.4 など) は `manual` になるので、`audit_site` を使ってください。
- `audit_site` がたどるリンクは、起点のページにあるものだけです。操作のあとに現れる画面は検査できません。ログインが必要なページには、`--storage-state` を使います。
- WCAG 2.1 を対象にしたとき、4.1.1 は、WCAG 2.1 の正誤表に従い、HTML のコンテンツでは常に満たすものとして扱います。
- WCAG 2.2 で追加された達成基準の検査は、目安による判定です。2.4.13 は、フォーカス表示の画素ではなく、`outline` の指定から判断します。3.3.8 は、パスワードの欄とよく使われる CAPTCHA の記述を探すもので、ログインの流れをたどることはしません。
- メディアや入力欄がページにないとき、関連する達成基準は「該当しない」と推定します。あとから読み込まれる要素は見落とすことがあります。
- `check_interaction` は、ページを移動する要求と GET 以外の要求を止めたうえで操作します。サーバー側のデータは変えませんが、GET で状態を変える作りのサイトでは影響が出ることがあります。
- ホバーで現れる内容は、250 ミリ秒以内に表示されるものだけを検出します。`title` 属性によるブラウザ標準の説明は対象外です。
- React、Vue、Angular のサンプルで、フレームワーク経由のイベント処理を検出できることを確かめています。React はイベントを 1 か所でまとめて受けるため、要素に付いた内部のプロパティから処理を読み取ります。同じ作りでプロパティを読めないフレームワークでは、2.5.1 と 2.5.2 が `needs_judgment` になります。
- `window` に直接登録したポインタの処理は検出できません。Playwright 自身が `window` に登録する処理と区別できないためです。
- 検査は Chromium だけで行います。
- 指摘が 0 件でも、達成基準を満たす保証にはなりません。最後は人の目と支援技術で確認してください。

## 精度

[W3C の ACT Rules のテストケース](https://www.w3.org/WAI/standards-guidelines/act/rules/)を使い、axe-core を単体で使った場合と kikori を比べています。対象は、WCAG の達成基準に対応する 63 のルールの、955 件のテストケースです。このうち 303 件が、不適合と期待されるものです。

| | axe-core 単体 | kikori の自動検査 | kikori とモデルの判断 |
|---|---|---|---|
| 対応するルールの数 | 37 | 43 | 56 |
| 不適合として報告できた件数 | 162 (53.5%) | 179 (59.1%) | 225 (74.3%) |
| 報告、または要確認として指摘できた件数 | 177 (58.4%) | 211 (69.6%) | 260 (85.8%) |
| 誤検出 | 0 | 1 | 7 |
| 適合率 | 100% | 99.4% | 97.0% |

モデルの判断まで使うと、報告できずに見逃す不適合は、axe-core 単体の 126 件から 43 件に減ります。増えた分の多くは、意味の判断が要るルールです。代替テキスト、リンクの文言、見出しとラベル、文字を画像にした箇所、言語の指定がこれにあたります。axe-core は、こうした文言があるかどうかは調べられますが、内容に合っているかどうかは調べられません。

この計測には、kikori の一部が表れにくくなっています。ACT のルールの多くは、ページのマークアップから読み取れることを対象にしています。そのため、リフロー、文字間隔、ホバーで現れる内容、ページどうしの比較のように、kikori がページを操作して調べる検査は、ほとんど測られていません。

左の 2 列は、すべて自動で求めた数字です。`npm run benchmark:act` で再現できます。

右の列は、意味の判断が要る達成基準を、呼び出し側のモデルが判断した場合の数字です。kikori はこの使い方を前提に作っています。今回は、Claude を別のエージェントとして動かして判断させました。渡した材料は、`collect_evidence` の結果とスクリーンショットだけです。期待される結果は伏せています。判断の内容は [docs/act-judgments.json](docs/act-judgments.json) に記録しています。モデルや実行する日が変わると、数字も変わります。この列は、1 回の計測の結果として読んでください。

モデルの判断を加えると、見つかる不適合が増える一方で、適合率は下がります。誤検出 7 件のうち 6 件は、モデルの判断によるものです。モデルが不適合と判断した箇所は、人が確かめる前提で扱ってください。字幕、音声解説、書き起こしに関するルールは、判断の対象から外しています。

これは、正式な ACT の実装報告ではありません。計測の方法と限界、ルールごとの数字は [docs/act-results.md](docs/act-results.md) (英語) にあります。

## 開発

kikori 自体を開発するときは、ソースからビルドします。

```sh
npm install
npm run build
node dist/src/index.js install
npm test
```

手元のビルドを Claude Code から試すには、`claude mcp add kikori-dev -- node /path/to/kikori/dist/src/index.js` で登録します。

`test/fixtures` に、問題のあるページと問題のないページを置いています。

`fixtures-src/frameworks` には、React、Vue、Angular で同じ不具合を仕込んだサンプルがあります。`npm test` の中で esbuild がまとめ、3 つとも同じ指摘が出ることを確かめます。

プルリクエストと `main` への push のたびに、GitHub Actions で同じテストが走ります。

コミットメッセージとプルリクエストのタイトルは、[Conventional Commits](https://www.conventionalcommits.org) に従います。種別は Angular の規約に合わせ、`build`、`chore`、`ci`、`docs`、`feat`、`fix`、`perf`、`refactor`、`revert`、`style`、`test` を使います。GitHub Actions が commitlint で確かめます。手元では `npx commitlint --from main` で確かめられます。

## リリースの手順

1. `package.json` の `version` を更新し (`npm version minor` など)、その変更を `main` に取り込みます。
2. `v` にそのバージョンを続けたタグ (`v0.2.0` など) で、GitHub のリリースを公開します。
3. リリース用のワークフローがテストを実行し、パッケージを npm へ公開します。

ワークフローは npm の trusted publishing で認証するため、リポジトリに npm のトークンを置きません。タグが `package.json` のバージョンと一致しないときは、公開せずに止まります。
